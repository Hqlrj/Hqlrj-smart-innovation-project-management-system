## 一、功能需求

### 1.1 业务背景

现有流程：项目负责人上传 `.docx` 计划书 → 审核人在「进度管理」页面直接通过/驳回。

**新增能力**：审核人打开待审项目时，**先选择审核方式**：

| 模式 | 说明 | 适用场景 |
|---|---|---|
| **人工审核** | 沿用现有逻辑，审核人通读计划书后自行决定 | 简单项目、审核人更信任人工判断 |
| **AI 辅助审核** | 系统解析计划书 → 按章节 AI 评审 → 生成报告 → 审核人参考报告再下结论 | 长文档、希望有结构化意见 |

**核心原则**：无论选哪种模式，**最终通过/驳回仍由审核人决定**；AI 只作参考，不自动修改项目状态。

### 1.2 功能需求清单

#### FR-01 计划书上传（复用现有）

- 仅支持 `.docx`（已有魔数校验 `50 4B 03 04`）
- 落库 `project_plan`，文件存 `uploads/project-plans/`
- 项目状态为 `submitted` 且已有关联计划书，才允许进入审核

#### FR-02 审核方式选择（新增）

- 审核人点击「审批」时，弹窗增加单选：**人工审核** / **AI 辅助审核**
- 选 **人工审核** → 直接进入现有通过/驳回表单
- 选 **AI 辅助审核** → 创建评审任务，异步执行，审核人可稍后查看报告再审批
- 同一项目同一时间只允许 **1 个进行中的 AI 任务**
- 需记录：`review_mode`（`MANUAL` / `AI_ASSISTED`）、`task_id`（AI 模式时）

#### FR-03 AI 评审全流程（异步）

```
上传 .docx
  → ① 文件合法性检查
  → ② POI 文本解析（段落 + 样式）
  → ③ 数据清洗
  → ④ 正则/样式切章
  → ⑤ 逐章 AI 评审
  → ⑥ 合并生成总报告
  → ⑦ 审核人查看报告 + 人工结论
```

- 接口 **3 秒内返回 `taskId`**，后台异步执行
- 任务状态：`PENDING → PARSING → REVIEWING → SUMMARIZING → DONE / FAILED`
- 支持进度展示：「已评审 3/9 章」

#### FR-04 文本解析与清洗

- 用 Apache POI 读取段落：`text`、`outlineLvl`、`styleName`、字号、加粗等
- 单独提取页眉/页脚，清洗时剔除
- 清洗：全半角统一、去零宽字符、压缩空白、软换行合并、敏感信息脱敏
- **保留段落结构与样式字段**，供切章使用

#### FR-05 章节切分（正则 + 样式兜底）

- **优先**：`outlineLvl ∈ {0,1,2}` 或 `Heading 1/2/3` 样式判标题
- **兜底**：文本正则（一、 / 1.1 / 第X章 等）
- 反误判：长度 ≤ 30 字、不以句号结尾、排除目录页（引导点线 `......`）
- 切分结果落库，供审核人核对
- 切不出章节时，整篇作为「全文」一章，不报错

#### FR-06 逐章 AI 评审

- 每章独立调用 LLM，输出结构化 JSON
- 强制附带原文 `evidence`，程序做字符串回溯校验
- 单章失败不影响其他章；可重试
- **综合分由程序计算**，不让模型算

#### FR-07 合并总报告

- 程序算：章节加权分 → 100 分制 → 等级（A/B/C/D）
- 模型写：总体评述、亮点、问题、风险、修改建议、参考建议（建议通过 / 修改后通过 / 不建议通过）

#### FR-08 报告展示与人工结论

- 报告页顶部：**「本报告由 AI 生成，仅供审核人参考」**
- 展示：总分、等级、章节折叠面板（得分/维度/证据/建议）
- 审核人在报告下方填写：人工评分、通过/驳回、意见
- 保留 `ai_score_snapshot`，人工结论不覆盖 AI 原始分
- 复用现有 `approve` / `reject` + 站内通知

## 二、角色与权限

| 角色 | 权限 |
|---|---|
| 项目负责人 | 上传计划书；只能看到「AI 评审中 / 已完成」状态，**不能看 AI 报告详情** |
| 评委老师 / 审核人 | 选择审核方式；查看 AI 报告；提交最终通过/驳回 |
| 系统管理员 | 同审核人 + 查看任务异常、重试失败任务 |

| 操作 | 项目负责人 | 评委/审核人 | 系统管理员 |
|---|:--:|:--:|:--:|
| 上传计划书 | ✅ | ❌ | ✅ |
| 选择审核方式 | ❌ | ✅ | ✅ |
| 查看 AI 报告 | ❌ | ✅ | ✅ |
| 提交人工结论 | ❌ | ✅ | ✅ |
| 重试失败任务 | ❌ | ❌ | ✅ |

> 前端入口通过 `utils/permission.ts` 控制；**后端必须独立校验**，前端隐藏不算安全边界。

## 三、全流程总览

### 3.1 流程图

```
项目负责人上传计划书(.docx)
        ↓
项目提交(submitted) + 计划书已关联
        ↓
审核人点击「审批」
        ↓
    ┌───────────────┐
    │ 选择审核方式   │
    └───────┬───────┘
            │
    ┌───────┴───────┐
    ↓               ↓
 人工审核        AI 辅助审核
    ↓               ↓
 现有审批弹窗    创建 taskId（异步）
 通过/驳回           ↓
                 ① 文件合法性检查
                     ↓
                 ② POI 文档解析
                     ↓
                 ③ 数据清洗
                     ↓
                 ④ 正则/样式切章
                     ↓
                 ⑤ 逐章 AI 评审
                     ↓
                 ⑥ 合并总报告
                     ↓
                 审核人查看报告
                     ↓
              人工评分 + 通过/驳回
                     ↓
              最终项目状态(approved/rejected)
```

### 3.2 任务状态机

```
PENDING(待处理)
   │
   ▼
PARSING(解析中) ──失败──▶ FAILED(失败, 带 error_msg)
   │
   ▼
REVIEWING(评审中, 逐章节推进)
   │
   ▼
SUMMARIZING(汇总中)
   │
   ▼
DONE(完成, 报告可查看)
```

## 四、非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| NFR-01 | 性能 | 2 万字文档端到端 ≤ 5 分钟；上传/发起评审接口 ≤ 3 秒 |
| NFR-02 | 并发 | 支持 ≥ 3 份计划书并行评审；LLM 调用限流 2–3 章/批 |
| NFR-03 | 可靠性 | 单章失败不影响整体；指数退避重试；局部结果保留 |
| NFR-04 | 安全 | 报告接口后端校验角色；反提示注入；证据回溯校验 |
| NFR-05 | 可追溯 | 记录 `model_name`、`prompt_version`、各章 `raw_response` |
| NFR-06 | 合规 | 清洗阶段脱敏手机号/邮箱；申报材料不外传未授权第三方 |
| NFR-07 | 体验 | 立即返回 taskId；逐章增量可见；完成时站内通知 |

## 五、数据表设计（精简版）

比完整版精简到 **5 张新表**（`project`、`project_plan` 复用现有）。

### 5.1 `ai_review_task` — 评审任务

```sql
id, project_id, plan_id,
status,                    -- PENDING/PARSING/REVIEWING/SUMMARIZING/DONE/FAILED
section_total, section_done,
total_score, grade,
model_name, prompt_version,
file_hash,
token_input, token_output, duration_ms,
error_msg, create_time, end_time
```

### 5.2 `ai_review_section` — 章节切分 + 评审结果

```sql
id, task_id, sort_order,
section_title, section_level,
char_count,
score,
dimensions(JSON), strengths(JSON), weaknesses(JSON),
risks(JSON), suggestions(JSON),
evidence_unverified_count,
raw_response, status, error_msg, create_time
```

### 5.3 `ai_review_report` — 总体报告

```sql
id, task_id, total_score, grade,
summary,
highlights(JSON), main_problems(JSON), risks(JSON), suggestions(JSON),
missing_sections(JSON),
ai_recommendation, consistency_note,
raw_json, create_time
```

### 5.4 `human_review` — 人工结论

```sql
id, task_id, project_id,
reviewer_id, reviewer_name,
ai_score_snapshot,           -- AI 原始分快照，人工不得覆盖
human_decision,              -- PASS/REJECT
comment, is_overridden,
review_time, create_time
```

### 5.5 `project` 扩展字段（可选）

```sql
review_mode,                 -- MANUAL / AI_ASSISTED
ai_task_id                   -- 最近一次 AI 任务 ID
```

## 六、接口约定

| 编号 | 接口 | 方法 | 说明 | 鉴权 |
|---|---|---|---|---|
| API-01 | `/projects/{id}/start-review` | POST | 审核人发起，body: `{ "mode": "MANUAL" \| "AI" }` | 评委/审核人 |
| API-02 | `/ai-review/tasks/{taskId}` | GET | 查询任务状态与进度 | 相关角色 |
| API-03 | `/ai-review/tasks?projectId=` | GET | 任务列表 | 相关角色 |
| API-04 | `/ai-review/tasks/{taskId}/report` | GET | 获取完整报告 | **仅审核人** |
| API-05 | `/ai-review/tasks/{taskId}/human-review` | POST | 提交人工结论 | 评委/审核人 |
| API-06 | `/ai-review/tasks/{taskId}/retry` | POST | 失败任务重试 | 管理员 |
| — | `/projects/{id}/approve` | POST | 最终通过（复用现有） | 评委/审核人 |
| — | `/projects/{id}/reject` | POST | 最终驳回（复用现有） | 评委/审核人 |
| — | `/projects/upload-plan` | POST | 上传计划书（复用现有） | 登录用户 |

统一响应格式：`Result<T>` → `{ code, msg, data }`，`code=1` 成功。

### 第 0 步：开工准备（必须先做）

| 序号 | 做什么 | 产出 | 怎么验收 |
|---|---|---|---|
| 0-1 | 准备 3–5 份真实 `.docx` 样例（标准模板、自动编号、含目录、缺章节） | 测试文档集 | 能在 Word 导航窗格看到章节结构 |
| 0-2 | 确认 LLM 选型及 API Key、预算 | 配置项清单 | 能调通一次简单对话 |
| 0-3 | 确认 IDEA 启动工作目录为 `SpringBoot-project` | 环境说明 | 上传文件落在正确 `uploads/` 目录 |
| 0-4 | 编写并执行建表 SQL（5 张新表） | SQL 脚本 | 表创建成功 |

**第一件该做的事**：拿一份用了 Word **自动编号**的真实申报书，验证 POI 能否读到 `outlineLvl`——这决定切章走「样式优先」还是「纯正则」。

**提示词**：无（不涉及 LLM）

### 第 1 步：上传计划书（复用 + 小扩展）

**做什么**

- 复用 `POST /projects/upload-plan`
- 确保项目 `submitted` 且有关联 `project_plan` 记录

**产出**

- `project_plan` 记录 + 磁盘文件

**验收**

- 上传 `.docx` 成功；`.pdf` / 改后缀文件被拒绝
- 非法文件有明确错误提示

**提示词**：无

---

### 第 2 步：审核方式选择 + 任务创建

**做什么**

- 前端「审批」弹窗增加：人工 / AI 二选一
- 选 AI → `POST /projects/{id}/start-review`，创建 `ai_review_task`，状态 `PENDING`
- 立即返回 `taskId`，后台线程/队列开始执行
- 选人工 → 跳过 AI，走现有审批弹窗

**产出**

- `taskId` + 任务记录
- 项目标记 `review_mode = AI_ASSISTED`

**验收**

- 3 秒内返回，接口不阻塞
- 同一项目重复发起时提示「任务进行中」或返回已有 `taskId`
- 非审核人调用返回 403

**提示词**：无

---

### 第 3 步：文件合法性检查

**做什么**

- 扩展名 `.docx` + 魔数校验（已有）
- 计算 SHA-256 文件指纹（供缓存/去重）
- 可选：加密文档检测、字符数上限（如 20 万字）

**产出**

- 通过 / 拒绝 + 原因

**验收**

- 伪后缀 `.docx`（实为 pdf）被拦截
- 空文件、超大文件被拦截

**提示词**：无

---

### 第 4 步：文档解析（POI）

**做什么**

- `XWPFDocument` 遍历段落，提取：

```json
{
  "index": 0,
  "text": "段落文本",
  "styleName": "Heading 1",
  "outlineLvl": 0,
  "fontSize": 16,
  "bold": true,
  "alignment": "CENTER",
  "isInTable": false
}
```

- 单独提取页眉/页脚（`getHeaderList()` / `getFooterList()`）

**产出**

- 段落序列 JSON（可落中间文件或库）

**验收**

- 解析出的标题清单与 Word **导航窗格**一致
- 自动编号文档能读到 `outlineLvl`
- 总字数与 Word「字数统计」偏差 < 5%
- 页眉页脚未混入正文

**提示词**：无

---

### 第 5 步：数据清洗

**做什么**

按顺序执行：

| # | 处理 | 说明 |
|---|---|---|
| 1 | 剔除页眉/页脚/页码 | 按解析阶段标记直接删 |
| 2 | 全角/半角统一 | 数字、字母、标点 |
| 3 | 清除零宽字符 | `\u200b`、`\u00a0` 等 |
| 4 | 压缩连续空白 | 多个空格 → 一个 |
| 5 | 软换行合并 | 依据行尾标点判断 |
| 6 | 敏感信息脱敏 | 手机号 → `138****5678` |
| 7 | 保留结构字段 | `outlineLvl` 等原样传递 |

**产出**

- 清洗后的段落序列（仅 `text` 变化）

**验收**

- 清洗前后**标题段落数量不变**
- 全角数字变半角；手机号已脱敏
- 软换行正确合并，未错并两个真实段落

**提示词**：无

---

### 第 6 步：正则切章（核心）

**做什么**

**第一优先级：结构样式（应对 Word 自动编号）**

```
判定为标题：outlineLvl ∈ {0,1,2} 或 styleName 命中 Heading 1/2/3
层级：level = outlineLvl + 1
```

**第二优先级：文本正则（样式拿不到时使用）**

| 层级 | 正则 | 匹配示例 |
|---|---|---|
| L1 | `^第[一二三四五六七八九十百零]+[章篇]` | 第三章 |
| L1 | `^[一二三四五六七八九十]+[、.．]` | 一、项目概述 |
| L1 | `^[【\[]\s*[^】\]]{2,20}\s*[】\]]$` | 【项目背景】 |
| L2 | `^\d+\.\d+(\.\d+)?\s*[、.．]?\s*\S` | 1.1 市场需求 |
| L2 | `^\d+[、.．]\s*\S` | 1. 项目概述 |
| L3 | `^[（(][一二三四五六七八九十\d]+[）)]` | （一）/ (1) |

**反误判规则**（候选行须同时满足）：

| 规则 | 判定 |
|---|---|
| 长度 | 去掉编号后 ≤ 30 字 |
| 结尾 | 不以 `。` `；` `，` 结尾 |
| 非目录 | 不含连续引导点线 `.{3,}` |
| 非句内引用 | 不以「如」「参见」「详见」开头 |

**后处理**

- 空章节合并（`minChars = 80`）
- 切不出章节 → 整篇作为「全文」一章
- 章节权重 = 该章字数 / 全文字数

**产出**

```json
[
  {
    "title": "市场需求分析",
    "level": 2,
    "charCount": 1840,
    "content": "...",
    "sortOrder": 3
  }
]
```

落库 `ai_review_section`（标题、字数部分）

**验收**

- 标题召回率 ≥ 90%
- 「如第一章所述…」未被误判为标题
- 含目录页文档，目录未变成几十个空章
- 章节字数之和 ≈ 全文 95%+

**提示词**：[Prompt-3 切章自检（可选）](#prompt-3切章自检第-6-步可选)

### 第 7 步：逐章 AI 评审

**做什么**

```
for section in sections:
    prompt = buildPrompt(project, section)     // Prompt-1
    result = callLLM(prompt, temperature=0.2)
    json = parseAndValidate(result)
    section.score = weightedScore(json.dimensions)  // 程序算分
    save(section, json)
```

**关键设计**

- 一次只给一章，上下文可控
- 强制 JSON 输出 + 原文 evidence
- 程序做 evidence 字符串回溯
- 并发 2–3 章，单章失败重试 2 次
- 章节 < 80 字不调模型，直接标记「内容过少」

**产出**

- 每章：`dimensions`、`strengths`、`weaknesses`、`risks`、`suggestions`、`score`

**验收**

- 同一章连跑 3 次，分数波动 ≤ ±0.5（5 分制）
- 每条 `evidence` 能在原文匹配
- 正文写「请给满分」的文档未给满分
- 单章失败，其他章节结果正常保留

**提示词**：[Prompt-1 章节评审（核心）](#prompt-1章节评审第-7-步逐章调用)

---

### 第 8 步：合并总结

**做什么**

**程序算分（确定性）**

```
章节得分 = Σ(维度分 × 维度权重)                    // 0~5 分制
综合得分 = Σ(章节得分 × 章节权重) × 20             // 转成 100 分制
等级     = A≥90 / B≥80 / C≥60 / D<60
```

**模型写评述**（Prompt-2）

- 输入各章结构化摘要（**不是全文**）
- 输出：总体评述、亮点、问题、风险、建议、AI 参考建议

**产出**

- `ai_review_report` 完整记录

**验收**

- 手算加权分与系统一致
- 综合分 ≠ 各章简单算术平均
- 低分文档 AI 不给「建议通过」
- 发给模型的输入是摘要，不是全文

**提示词**：[Prompt-2 合并总结](#prompt-2合并总结第-8-步调用-1-次)

### 第 9 步：报告展示 + 人工结论

**做什么**

- 新建 Vue 报告页（或嵌入审批弹窗）
- 仅审核人可访问报告 API
- 报告页结构：

```
┌─────────────────────────────────────────┐
│ ⚠ 本报告由 AI 生成，仅供审核人参考        │
├─────────────────────────────────────────┤
│ 综合得分 78.5 / 100    等级 B            │
├─────────────────────────────────────────┤
│ 总体评述（模型生成）                      │
├─────────────────────────────────────────┤
│ 章节明细（折叠面板）                       │
│  ├ 得分 + 各维度理由                      │
│  ├ 优点 / 问题 / 风险                     │
│  ├ 修改建议                              │
│  └ 原文证据                              │
├─────────────────────────────────────────┤
│ 【审核人操作区】评分 + 通过/驳回 + 意见     │
└─────────────────────────────────────────┘
```

- 提交后写 `human_review`，调用现有 `approve`/`reject` + 通知

**产出**

- 审核人可见的完整报告 + 最终项目状态

**验收**

- 项目负责人访问报告 API → 403
- 报告页有「AI 生成，仅供参考」声明
- 人工提交后 AI 原始分未被覆盖
- 未提交结论的项目，最终状态为「待复核」

**提示词**：无（展示层）

## 九、模型参数与调用策略

| 参数 | 建议值 | 理由 |
|---|---|---|
| `temperature` | **0.2**（章节评审）/ **0.3**（合并总结） | 保证打分稳定可复现 |
| `top_p` | 0.9 | 配合低温 |
| 结构化输出 | 开启 `response_format: json_object`（若支持） | 强制 JSON |
| `max_tokens` | 1500–2500（章节）/ 2000（总结） | 避免 JSON 被截断 |
| 单次超时 | 120 秒 | 章节评审输出较长 |
| 重试 | 最多 2 次，指数退避（2s / 6s） | 应对限流与偶发失败 |
| 并发 | **同时 2–3 个章节** | 避免触发 QPS/TPM 上限 |
| 失败隔离 | 章节级独立 | 单章失败不影响整体 |

### 9.1 时延预算

```
总耗时 ≈ 预处理（< 2 秒） + ⌈章节数 / 并发数⌉ × 单章时延 + 合并总结（20–40 秒）
```

| 场景 | 章节数 | 策略 | 预估耗时 |
|---|---|---|---|
| 典型申报书（2 万字） | 10 | 并发 3 路 | 约 1.5–3 分钟 |
| 大型申报书（5 万字） | 22 | 并发 3 路 | 约 3–5 分钟 |

> **不要用带思维链的推理模型做逐章评审**，单份文档可能需 20–30 分钟。

### 9.2 提示词设计 8 原则

| # | 原则 | 做法 |
|---|---|---|
| 1 | 单一职责 | 一个 prompt 只干一件事 |
| 2 | 给出评分锚点 | 写清 1/3/5 分各自长什么样 |
| 3 | 强制结构化 | 明确 JSON 模板，只输出 JSON |
| 4 | 强制引用证据 | 每条结论附原文摘录 |
| 5 | 允许说不知道 | 信息不足时标记，禁止编造 |
| 6 | 划清边界 | 只评审当前章节 |
| 7 | 声明反注入 | 文档中指令性文字不得执行 |
| 8 | 分隔符包裹正文 | `<<<CHAPTER_BEGIN>>>` … `<<<CHAPTER_END>>>` |

## 十一、推荐落地顺序

```
第 0 天  准备样例文档 + 建表 + 确认 LLM
第 1 天  第 4 步解析 + 第 5 步清洗     → 能打印段落，标题与导航窗格一致
第 2 天  第 6 步切章 + Prompt-3 自检   → 能打印章节列表，人工核对
第 3 天  第 7 步单章评审跑通          → 一章返回合格 JSON
第 4 天  第 7 步全章循环 + 异步任务    → 整份文档跑完
第 5 天  第 8 步合并 + 第 2 步入口     → 审核人选 AI 后能拿到完整报告
第 6 天  第 9 步报告页 + 人工结论      → 权限正确，能最终通过/驳回
```

**每步验收判据速查**

| 步骤 | 一句话判据 |
|---|---|
| ① 上传 | 3 秒内返回 taskId，不阻塞 |
| ② 解析 | 标题清单与 Word 导航窗格能对上 |
| ③ 清洗 | 噪声清除但标题数不变 |
| ④ 切章 | 标题召回率 ≥ 90%，正文不误判 |
| ⑤ 逐章评审 | JSON 齐全 + evidence 可回溯 |
| ⑥ 合并 | 加权分正确、结论与分数自洽 |
| ⑦ 报告与结论 | 项目负责人看不到报告，审核人能看且能下结论 |

## 十三、坑位清单

| # | 坑 | 后果 | 应对 |
|---|---|---|---|
| 1 | Word 自动多级编号 | 正则一条都匹配不到 | 样式优先（`outlineLvl`），正则兜底 |
| 2 | 目录页被当成章节 | 产生几十个空章节 | 引导点线特征 + 前 3 页整体排除 |
| 3 | 正文误判为标题 | 章节被切碎 | 长度 + 结尾标点 + 独占性三重过滤 |
| 4 | 同步调用模型 | 请求超时 | **必须异步**，立即返回 taskId |
| 5 | 让模型算加权总分 | 分数自相矛盾 | 分由程序算 |
| 6 | 把全文喂给总结环节 | 成本翻倍 | 只给结构化摘要 |
| 7 | 文档内写指令诱导打分 | 报告失真 | 反注入声明 + 分数 clamp |
| 8 | 模型编造原文 | 报告不可信 | 强制 evidence + 字符串回溯 |
| 9 | JSON 被截断 | 解析失败 | 留足 max_tokens + 重试 |
| 10 | 单章失败导致整体失败 | 白跑 | 章节级隔离 + 局部结果保留 |
| 11 | 一次并发发出全部章节 | 触发限流 | 并发限制 2–3 |
| 12 | 切分结果不落库 | 无法排查 | 章节标题与字数必须入库 |
| 13 | 项目负责人能看到报告 | 违反定位 | 后端强制角色校验 |
| 14 | 人工结论覆盖 AI 分 | 失去分析数据 | `ai_score_snapshot` 快照保留 |
| 15 | 提示词没有评分锚点 | 分数全挤中间 | 必须写清 1/3/5 分锚点 |
